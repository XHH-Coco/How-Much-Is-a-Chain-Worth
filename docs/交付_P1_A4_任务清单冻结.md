## 3. 口径锁定：主表 **8 任务 × 5 臂**（Q-01 结案 → D-17）

**结论：主表是 8 个任务 × 5 条臂（A1 地板 / A2 常规 / A3 图 / A4 语言模型 / A5 链信息）。**

三条独立证据（不是"多数票"）：

1. **臂的集合定义在 Proposal §6**，那里列的是 A1–A5 五条；"4 臂"只出现在两处排期/工时文字里。
2. **§5 的 H3 需要 A5**："信息胜过架构"的全部意义就是"注入链信息 vs 换更强架构"。A5 掉出主表，H3 就不在主表里了。
3. **§8 的主表（图 6）与 §7.1 的分工都按 5 条写**：C 跑 A1/A2/A5、B 跑 A3/A4，五条各有主。

**那"96 次经典 + 48 次 GNN = 144"怎么办？** 它按官方评估单元复算**只可能是 3 条臂**：

| 量 | 复算 | 结论 |
|---|---|---|
| 每臂次数 | PolyBench 6 × 1 个官方 70/30 × 3 种子 = 18；PB26 2 × 5 折 × 3 种子 = 30；合计 **48** | 48 是**每臂**的 |
| 144 | 96 经典 = 2 臂 × 48；48 GNN = 1 臂 × 48 → **3 臂** | 与 4 臂、5 臂都不符，是旧稿 |
| 150 | 150 − 144 = **6 次无出处** | 正是 Q-02 原话"差 6 次" |
| 778（全队总） | 150 + 48 + 100 + 30 + 225 + 225 = 778 | 778 里含的是 150，不是 144 |

**所以本快照只冻结"哪些任务、哪些臂"，不冻结"总共多少次拟合"。** 那个数同时牵动 C 的 22.0 pH 与 D 的审计口径，归 **Q-02（C 定）**，
他要在 P2 预算表定稿时按"每臂 48 × 实际臂数"重算，并说明 A1 地板、A5 注入是否各自独立成格。
**在那之前，"192""240""107"这类数字一个都不许出现在文档里**——本快照里没有，也请不要补。

## 4. 三条这次才查清、会改变后来做法的事实

### 4.1 PolyMetriX Tg **本来就是开尔文**——禁止再加 273.15（D-18）

A-3 交付文档 §7 第 4 条写的是"PolyBench26 的 PolyMetriX Tg 也必须用同一条 `T + 273.15`"。**那是一个预设，实测不成立。**

| 证据 | 内容 |
|---|---|
| 源表列名 | `data/raw/polybench26/Datasets/PSMILES/PolyMetriX/Tg/Tg.csv` 只有两列：`smiles, Tg_K` |
| 实测分布 | 7,367 行、**0 缺失**、134.15 ~ 768.15 K、中位 410.15 K（= 137 ℃） |
| 官方文档 | `DATA_PROVENANCE.md` 记该文件是 `labels.Exp_Tg(K)` 列的精确投影；**列名自带 `(K)`** |
| 反向检验 | 若这段数值是 ℃，最小值 134 ℃ 尚可、最大值 768 ℃ 就已超过任何聚合物的分解温度；而 134.15 K（−139 ℃）正好是 PDMS 量级、768.15 K（495 ℃）正好是 PBI 量级 |

**加 273.15 会让整个 PolyMetriX Tg 任务偏 273 K，而不会报任何错。** 这条已写进 YAML 的 `unit_evidence`，
并用 `tests/test_task_configs.py::test_polymetrix_tg_is_already_kelvin` 守着；A-3 交付文档 §7 第 4 条同时加了勘误。

### 4.2 密度的单位**官方没声明**——所以我们不写单位（D-19）

`pb26_homopolymer_density` 的 `unit_status: unverified`、`target_unit: null`。查过的地方：

- 仓库 `README.md`（Properties Covered 只列性质名，不列单位）
- `DATA_PROVENANCE.md`（只讲来源与许可）
- `SCALING_EXPERIMENTS_METHODS.md`（只讲档位、折、模型，不列单位）
- 源 `Cleaned_OMersBench_v3_final.jsonl` 的 `outputs.density`（只有数值，如 `1.1222596573`）

数值量级"看起来像" g/cm³，但 A-3 已经在 `bandgap chain_Egc` 上立过规矩：**"唯一说得通的解释"仍是推断，不是证据**（D-16）。
所以这里**不写单位**，并规定：报告这一列时必须标"官方未声明单位"；谁拿到一手证据（比如 OPoly26 数据集文档的单位声明）就追加一条决策，**不许就地改 YAML**。

**机制实验两个任务用的是第三种状态 `not_required`**：`pb26_scaling_cp` 与 `pb26_arch_transfer_ea` 只比较"同一性质内部"的 RMSE 排序，
单位不进入 κ（一个对数斜率）、不进入 Λ（R² 的函数）、不进入排序判决——**为了这种任务去猜一个单位，是纯粹的风险没有收益**。

### 4.3 PolyBench26 的 `n` 不是抄的：官方 `manifest.json` 就是它

三个 PB26 任务的 n 全部取自官方 `scaling_indices/**/seed_42/manifest.json` 的 `n_rows`，并在校验器里**逐项对过**：

| 任务 | 官方 `n_rows` | 官方 `train_sizes` | 官方 `target_column` |
|---|---:|---|---|
| `pb26_polymetrix_tg` | 7,367 | 300 / 1000 / 3000 | `Tg_K` |
| `pb26_homopolymer_density` | 1,800 | 300 / 1000 | `density` |
| `pb26_scaling_cp`（交替 Cp） | 27,802 | 300 / 1000 / 3000 / 10000 | `Cp` |
| `pb26_scaling_cp`（均聚 Cp） | 1,800 | 300 / 1000 | `Cp` |

这些不是"我们数的"，是**官方索引文件自己写的**——这是最强的来源，也意味着一旦官方换版本，校验器会立刻红。

| 基准 | 要产出的路径（已写在 YAML 的 `split_ref`） |

| OpenPoly（3 个） | `splits/openpoly/<task_id>_official.json` |

| 机制 arch | `splits/polybench26/arch/` **留空**（官方只发布物化脚本，D-08），快照里注明"本地物化、不入库" |

**落盘之后必须做一件小事**：把这些 YAML 的 `split_status` 从 `pending` 改成 `present`，重跑 `--verify`
（校验器会检查文件是否真的存在），并出 `configs/tasks` 的 v2 指纹。**只改状态不改指纹 = 冻结物被改而不留痕。**

### B / C（建模）

```python
from chainworth.io.tasks import load_task_config          # 读一份；字段错了当场抛错
cfg = load_task_config("configs/tasks/pb_t1_tg.yaml")
cfg["data_ref"]      # 读哪个文件
cfg["target_column"] # 读哪一列（PolyBench 是 `label`；PB26/OpenPoly 是官方列名）
cfg["target_unit"]   # 单位；None 表示官方没声明，别自己补
cfg["arms"]          # 这个任务要跑哪些臂
```

**三条不许违反的用法**：

1. **`target_unit` 为 `null` 时不要打印单位。** 那是"官方没声明"，不是"没有单位"。
2. **`n_labels` 就是 Λ 的分母**，不要用文件行数代替（bandgap 的 3,380 行 vs 0 可用就是反例）。
3. **`arms` 是名单不是建议**：`op_*` 只有 A2/A3（H4 只比经典 vs 图），`pb26_scaling_cp` 只有 A2——按名单跑，别"顺手多加一条臂"，那会让 κ 的曲线变成两个实验混在一起。
