## 1. 为什么可以先判定「可信」

重跑之前，三项身份值先被比对一遍。这三项分别锁住「输入」「特征」「划分」，任何一项不同，
后面的数字都不必再比：

| 身份 | 值 | 含义 | 判据 |
|:--|:--|:--|:--|
| `canonical_sha256` | `632aa02dc773942e103d8fc0c4bdefe6afddfb76151b33c99f70963868926068` | `canonical_train.csv` 的**字节哈希**（来自上游 6,478 行） | 输入、去重、排序、CSV 序列化全同 |
| `pack_sha256` / `features_sha256` | `fed6173b823ad37070d321ca9b072c97cda41b25aae6a1e7293be337045a76de` | `id_features.parquet` 的字节哈希（6,478 × 2,253） | RDKit 描述符 + 指纹 + parquet 序列化全同 |
| `split_version` | `ad424d721b9c@splits/polybench26/arch/seed_42/fold_00.npz` | 每折 npz 的字节哈希 | 官方 5 折的切分与落盘全同 |
| `source_manifest_sha256` | `4f513a738e32655adecc116a544e0500f15b24668260d00db0bf5909139e204b` | `generated/shared_splits/manifest.json`（官方脚本自写的划分清单） | 折的元数据、行数、两档计数全同 |

四项**全部逐位相同**。所以「本机重跑会不会造出一个不同的版本」这个问题，在跑训练之前就已经有答案了。

**纯计算约 8 分钟**（不含网络）。下面四个坑，前两个的答案**当时就写在 `docs/Arch Materialization.md` §6 里**，
是我执行时图快、只照着 `00c` 的取件清单跑，跳过了一步。记在这里是因为下一个人很可能犯同样的错：
**清单只记上游字节，不记派生步骤；顺序与前置条件写在文档里，不在脚本里。**

### 坑 1（文档已有）：「取件清单」不等于「物化所需输入」

`create_task4_shared_splits.py` 的默认 `POLYVERSE_WPSMILES` 指向
`Datasets/wPSMILES/polyVERSE/electron_affinity/electron_affinity_data_polymers_v4.csv`。
`00c` 的 `FILES` 里只有 `PSMILES/` 版（11,270 B），没有 `wPSMILES/` 版——因为**这一份是派生数据，
不是上游字节**，取件清单按设计不收它。

去上游取会返回 152 字节，那是 jsDelivr 的 404 正文：**这个路径在上游根本不存在**。
正确做法（§6 第 0 步写着）是用上游自带的 `PSMILES_to_wPSMILES.py` 生成：

```
python PSMILES_to_wPSMILES.py \
  data/raw/polybench26/Datasets/PSMILES/polyVERSE \
  data/raw/polybench26/Datasets/wPSMILES/polyVERSE \
  --pattern electron_affinity_data_polymers_v4
```

生成 368 行，wPSMILES 形式为 `[*:1]Cc1ccc(Cc2ccc([*:2])s2)cc1|1|<1-2:1:1<1-1:0:0<2-2:0:0`，
`electron_aff` 逐行与 PSMILES 版相同。

注意该脚本会 `drop_duplicates("smiles")`，而 `read_polyverse` 要求两份行数相同。本例 368 行无重复，
去重不改变行数；若将来换数据集，这一条要先查。

### 坑 2（新）：官方划分脚本的 `mkdir` 不幂等

`create_shared_splits()` 里是 `output_dir.mkdir(parents=True)`，没有 `exist_ok=True`。
上一次失败留下的**空目录**会让重跑直接 `FileExistsError`。删掉空目录再跑即可，或补 `--overwrite`
（但它会 `shutil.rmtree` 整个输出目录）。

### 坑 3（文档已有，但没说"不跑会怎样"）：`arch --setup` 不含组分特征

`--setup` 只做两件事：`materialize_splits()` + `build_id_features()`。
683 个组分的 `component_features.parquet` 与 `component_index.csv` 由 `00d_arch_components.py` 生成
（§6 第 2 步）。跳过它，`arch --ood` 会在第一行就退：

```
RuntimeError: 组分覆盖不完备：missing=['*C1=CC(=O)C(*)=CC1=O', ...]
```

这个断言是好的——它把「组分缺特征」拦在合成之前，而不是让官方脚本吐出权重和不为 1 的预测。
**建议在 §6 补一句"不跑 00d 会在这里退"，并把这个错误原文抄进去**，方便搜到。

### 坑 4（新）：网络对大文件不稳

`raw.githubusercontent.com` 对 6.8 MB 的 `dataset.csv` 连断两次（`SSLEOFError` / `RemoteDisconnected`），
分块 `Range` 请求也失败（对端直接关连接）。换 jsDelivr 镜像一次成功，**下载后按清单的 sha256 核对**
（`6f9d4d8c0cb8154a2150235569ba71f116f9bda1417303e19184e46d64a8bc46`，6,786,557 B），一致才落位。
换源不改变字节，哈希是判据。`00c` 本身是幂等的（已缓存的跳过），但单次请求失败会让整轮白跑——
建议给它加 `--retry`，或干脆改成分块。

## 5. 顺带修掉一个测试 bug

物化完成后，`test_run_records.py` 里那条**防分诊放水**的反向测试**仍然 skip**：

```python
arch_dir = REPO / MATERIALISED_NOT_COMMITTED[0]
if not arch_dir.is_dir() or not any(arch_dir.glob("fold_*.npz")):   # ← glob
```

实际物化落在 `splits/polybench26/arch/seed_42/fold_XX.npz`（`seed_42` 子目录，记录的 `split_version`
写的就是这个路径）。扁平 `glob` 永远匹配不到，于是这条闸在**任何**机器上都不会跑。
改成 `rglob`：

```
before: 15 tests, 12 passed / 3 skipped
after:  15 tests, 15 passed / 0 skipped（含 test_materialisation_present_means_green）
```

这一条与 D-62 是同一类病的两个面：D-62 修的是「缺件被当成错」，这条修的是「有件也不跑」。
两者都不报错，只有站在物化机上跑一遍才会露出来。

## 8. 留给下一个人的两句话

1. **「不入库」的产物必须写清在哪台机器**。这次能救回来，是因为重跑链路是确定性的；如果换一台
   RDKit 构建不同的机器，`pack_sha256` 就会变（D-59 的 `host_sensitive`），那时就没有「重跑一遍」这条路了。
2. **官方脚本不是幂等的**。`mkdir` 不带 `exist_ok`、脚本顺序有隐含依赖（`00d` 必须单独跑）。
   把链路写进文档时，顺序与前置条件要和命令一起写，不能只写命令。
