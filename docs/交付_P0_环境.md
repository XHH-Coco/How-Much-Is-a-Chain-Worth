> **两层锁为什么分开**：conda 管 Python 本身、pip、setuptools、编译好的二进制；pip 管全部科学计算包。同一个包如果两层都写，升级时会出现"谁说了算"的争议，所以除了 pip 自身（见 §4 第 4 条），每个包只在一层出现。

## 4. 与计划不一致的地方（都是刻意的）

**1）用了两层文件锁，没有用 `conda-lock`。**

原计划是 `conda-lock` 产 `lock/*.lock.yml`。实际尝试后放弃，有两条硬原因：

- `conda-lock` 3.0.4 解析 `environment.yml` 的 pip 段时**不支持 `--index-url` / `-f` 这类行内选项**——我们的 `gnn.yml` 与 `polybert.yml` 正是靠它们把 torch 指向 cu121、把 `torch-scatter`/`torch-sparse` 指向 PyG 索引。它会把这两行丢掉，再"成功"生成一个 **torch 会装成 CPU 版**的锁。**一个悄悄错的锁，比没有锁更危险。**
- 它依赖的 PyPI↔conda 名称映射（`raw.githubusercontent.com/regro/cf-graph-countyfair/.../grayskull_pypi_mapping.json`）当前返回 404，链路上取不到。

替代方案是 `conda list --explicit`（conda 层）+ `pip freeze`（pip 层）。取舍见 §5 第 1 条。

**2）GNN 环境是 Python 3.11.18，另两个是 3.10.14。** `chemprop 2.x` 全部版本要求 ≥3.11，`1.x` 要求 <3.9，3.10 上不存在可装版本，而 A3 臂依赖它。已获仓库所有者同意后重建。

**3）`gnn.yml` 钉了 `setuptools==75.8.0`。** `lightning_fabric`（`pytorch-lightning 2.3.0` 的依赖）仍 `import pkg_resources`，而 setuptools ≥81 已删该模块。不钉上限时 `import pytorch_lightning` 直接 `ModuleNotFoundError`，且 `pip check` 抓不到（它不算声明依赖）。

**4）`pip` 在两层锁里都出现。** conda 层的记录是 `pip 26.2.2`（pip 自降级后 conda-meta 没跟着改），pip 层第一行钉回 `24.3.1`。这是刻意保留的双写：conda 层负责给一个能用的 pip，pip 层负责把它降到声明的版本。除此之外没有第二个包被两层同时声明。

**5）Core 补了 `PyYAML==6.0.3`。** 原 `core.yml` 漏了它，而 P3 要读 `configs/**/*.yaml`——不补的话，到写配置那天才发现读不了 YAML。版本对齐 GNN / Polybert 里已有的 6.0.3，避免 YAML 1.1 行为在三套环境里不一致。

## 5. 已知局限（写在这里，免得以后被当成没发生过）

1. **是"版本级锁"，不是"哈希级锁"。** pip 层只有 `==` 版本号，没有每个 wheel 的 sha256。要做到"连下载的字节都一样"，需要 `pip download` 全部 wheel 再 `--require-hashes`——torch 单包 2.4 GB、两个环境各一份，约多花 2 小时机器时间。**当前口径：同平台同 Python 版本可复现到版本级；跨平台不复现。**
2. **只锁了 `win-64`。** 若有人用 Linux/macOS，锁文件不适用，只能按 `environment/*.yml` 重新装并在 `docs/DECISIONS.md` 记一条。
3. **锁是"从装好的环境反向导出"，不是"从声明正向求解"。** 好处是与磁盘 100% 一致；坏处是声明里写错的东西（例如第 4 节第 5 条那个漏掉的 PyYAML）锁里也不会有——**必须有人先发现**。这也是为什么 A-1 的验收标准要求"旁人按 `.yml` 重建后 diff"。
4. **`results/env_fingerprints/` 里现在只有环境指纹，没有 run 指纹。** 每跑一次实验再落一份 `<run_id>.json` 是 P5 的事，那时代码里要有 `verify_env.py` 做双向断言（既防高也防低）。
5. **polyBERT 的 7.3 GB 权重没有下载。** 那是 `分工_B` 的 P1 任务，不是环境阶段。
