## 0. 一句话

**"谁进训练集、谁进测试集"这件事，现在全部可追到官方发布物——PolyBench 10 个任务的测试集从平台接口取回、按 RDKit 规范 SMILES 对回行号；PolyBench26 的 4 份官方索引原样拷进仓库并用官方 `canonical_sha256` 验收；OpenPoly 因为官方没发布划分而**明确停住**，没有自己切一刀。**

## 2. 四步，顺序不能换

分工书把 A-5 写成四步。实际执行时每一步都卡住过一次，卡点写在这里，比"已完成"有用。

### ① 物化 canonical PSMILES 表（这一步原来不在条目里）

官方**不发布** canonical 表，只发布 compact 源（`Cleaned_OMersBench_v3_final.jsonl`）+ 生成脚本。而官方索引存的是**行号**——行号只在那张表的特定顺序下指向正确分子。所以先跑官方 `OMers_convert_jsonl.py`（2 分 29 秒，生成 **49 张表**）。

**卡点**：Windows 下 pandas 的 `to_csv` 按 `os.linesep` 写行尾，落盘是 CRLF；而官方 `canonical_sha256` 是按 LF 算的，官方 `manage_scaling_indices.py verify` 更是直接比字节。第一次跑，官方自检直接报 `Canonical source checksum mismatch`。
**处置**：把**生成物**（不是下载物）统一写成 LF。归一之后 `PSMILES/MD_5000/density/homopolymer_density.csv` 的 sha256 = `b8a576b9…b34b7`，与官方 `canonical_sha256` **逐位相等**（D-21）。

### ② 用 `canonical_sha256` 验收（不过就停）

4 张被校验的表全部对上：

| canonical_source | 官方 canonical_sha256（前 12 位） | 结果 |
|:--|:--|:--|
| `PSMILES/PolyMetriX/Tg/Tg.csv` | `b6d2b9f83419` | ✅ 就是 A-2 已发布的那份，无需另生成 |
| `PSMILES/MD_5000/density/homopolymer_density.csv` | `b8a576b9fa27` | ✅ 本地物化后归一，逐位相等 |
| `PSMILES/MD_5000/Cp/alternating_Cp.csv` | `7dad9d1dc0e9` | ✅ 同上（27,802 行） |
| `PSMILES/MD_5000/Cp/homopolymer_Cp.csv` | `0b09e47df3b6` | ✅ 同上（1,800 行） |

### ③ 取回 PolyBench 官方测试集并对成行号

官方那一半只有一个来源：平台前端 *Download Test Set* 按钮背后的接口
`GET http://202.98.16.11/api/dataset/test-download?file_name=<数据集名>.csv`，返回两列 `polymer_name,SMILES`（**不含标签**）。

关键一步是把 SMILES 对回 A-3 那张表的行号。三条断言缺一不可：① 调和表按 `source_row` 升序；② 每个测试 SMILES 都能规范化且**唯一命中一行**；③ 命中数等于测试集行数。三条全过才写文件——半份划分比没有划分危险。

**顺带查清的一件事**：`&seed=0/1/2` 三次请求返回的字节**完全相同**。所以"`eval_unit` 里的 ×3"只能是**模型初始化种子**，不是三份划分（D-20）。这一条不澄清，B/C 会把 3 次训练变成 9 次，而 9 份里没有一份是官方的。

### ④ 快照 PolyBench26 索引 + 官方自检

4 份 `seed_42/` 原样拷进 `splits/polybench26/`，逐文件核 sha256，旁边写 `PROVENANCE.json`（commit、源目录、每个文件的 sha256、`canonical_source`、`canonical_sha256`、折数、档位）。然后跑官方自检：

```
$ python .../manage_scaling_indices.py verify --indices-root splits/polybench26 --allow-missing-sources
Verified 4 compact scaling-index packages.
```

## 5. 校验：一条命令，四个层次

```bash
PYTHONPATH=src python scripts/03_splits.py --verify --deep
# → 校验通过 / verification passed（deep=True），退出码 0
```

| 层 | 查什么 | 谁在用 |
|:--|:--|:--|
| 结构 | 互斥、覆盖 0..n−1、无重复、比例 30%±0.5pp | `verify_splits()` |
| 指纹 | 每份 JSON 的 sha256 与 `splits_manifest.csv` 是否一致（改一个字节就红） | 同上 |
| 重算 | `--deep`：拿官方 CSV 重算行号，与落盘逐个比对 | 交付前、A-3 表重建后 |
| 外部 | 官方 `manage_scaling_indices.py verify` + `diff` 级字节比对（splits 拷贝 vs `data/raw`） | 同上 |

`--deep` 默认关闭只有一个理由：它要跑近 9,300 次 RDKit 规范化。实测整条 `--verify --deep`（含官方自检）约 **5 秒**——不慢，但它依赖 `data/interim/`（不入库），所以 CI 里用非 deep 版本，交付前手跑 deep 版本。

### 9.1 为什么改判

原判（D-22）的依据是一句话："**官方连划分规则都没发布**"。复核四处在手来源后，这句话不成立。

|:--|:--|
| **论文正文**（*Chin. J. Polym. Sci.* 2025, 43, 1749–1760，METHODS → Model Training Protocols） | **规则写得很清楚**：8:1:1 随机划分；每个性质的**数值域切成 10 个等宽箱**、箱内按比例抽；所有模型共用同一份划分 |
| GitHub 全树（`ccaa669`，`truncated:false`） | 39 个条目 = 26 文件 + 13 目录，**没有 `experiment_dataset/`**，连 `.gitignore` 都没有；`__pycache__` 的 `.pyc` 都被提交了 → 作者是整目录上传，缺的目录是**真没传**，不是被规则排除 |

| Zenodo `10.5281/zenodo.15551637` / 期刊页 | 记录里只有 1 个文件 `trained_model.zip`（460 MB 权重）；期刊页**无 Supplementary Information、无 data availability 章节** |

**准确的说法**：规则已公布且可复现；那一份具体划分、它的生成代码、以及随机种子，都没有发布。前者可做，后者不可做——这两件事原来被当成了一件。

### 9.3 为什么这不算踩 Proposal §7.5 红线

红线禁的是「**不读官方划分、自己随手切**」，它防的是"没人报错但结果全错"；对立面是**隐去来源**，不是禁止复现已公布的规则。四条同时成立才算过关：

1. 切法**逐字来自期刊正文**，不是我们发明的；
2. 种子**全公开**，每份带 `bin_edges` 与 `bin_counts`，任何人 `--source openpoly` 可逐位复现；
3. 状态名就叫 `rule_replicated`，不叫 `present`；目录里若出现 `*_official*.json`，测试直接变红；
4. 配置 `notes` / `README.md` / `PROTOCOL.json` / 论文限局一节**四处都写明"不是作者那一份"**。

反过来，"随手按 8:1:1 切一刀"为什么仍然不行：没有引文、没有种子、没有箱边界、不可重算，而且没人在文档里承认过——那才是 §7.5 要防的东西。

### 9.4 复现对不对怎么验收（不靠自觉）

官方仓库发布了 `results/final_model_test_performance_summary.csv`，XGBoost 那三行正好是 H4 的三个性质：

| 任务 | 官方 XGBoost 测试 R² |
|:--|--:|
| `op_tg` | **0.904375715** |
| `op_dielectric_constant_total` | **0.86** |
| `op_tm` | **0.807551835** |

特征与模型：`XGBRegressor(random_state=42)`（这条**有据**：notebook 里写死了 `random_state=42`）。
指纹参数则**不可考**：官方特征取自 `data.morgan_fp`，打包在未发布的 `.pt` 里，公开代码查不到半径与维度。
本仓库统一用 Morgan `radius=2` / `2048` 位（RDKit 新版生成器默认值），**这是我们的选择、不是官方设置**
——详见 A-6 交付文档 §6 第 3 条与 `docs/DECISIONS.md` D-25。比对因此只能看量级与区间，不能当"复现了他们的特征"。
**规则**：10 份各跑一遍，官方值应落在 min–max 区间内（或偏离 ≤0.05）。落不进去 = 规则读错了，回头核对 `PROTOCOL.json`，**不许调参凑数**。

### 9.5 残留局限（写进论文的"Limitations"）

1. **不是作者那份划分**，绝对 R² 不可与论文逐位对比。H4 比的是同一划分内两臂之差（Λ），划分是共同项不是混淆项——但不能声称"我们复现了他们的 0.9044"。
2. **Tm 测试集只有 17 条**。单份划分的 R² 方差很大，这正是要报 10 份区间而不是单点的原因；也顺带回答了论文自己承认的缺陷（"未进行多次随机划分"）。
3. **结构泄漏**：741 行只有 656 个原始串 / **585 个 RDKit 规范结构**（A-7），官方规则不按结构分组。按规范式实测跨集重复结构（seed 0）：Tg **28 个**、Tm **17 个**、介电总 **0 个**；10 个种子分别是 Tg 24–36、Tm 14–21、介电 0。每份文件的 `leakage` 字段记账，不遮掩。
   **口径说明（D-28）**：本文件 2026-11-12 早先记的是「Tg 15 / Tm 14」，那是按**原始 PSMILES 串**数的——同一根链换一种写法就被算成两个结构，等于把泄漏报低近一半（Tg 15 → 28）。同日按规范式重算并改记，**划分成员一个没动**（30 份的 `train_index`/`val_index`/`test_index`/`source_row` 逐份比对全等）。
4. **`n = all` 的口径**：固定测试集占 10%，所以训练池是 90%。C/D 算 Λ 的分母时对齐文件的 `n_train`/`n_test`，不要用 `n_labels`。
