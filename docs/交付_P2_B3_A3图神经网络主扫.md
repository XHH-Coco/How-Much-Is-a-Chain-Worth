## 3. 五个口径（改任何一个都等于换了一条臂）

**① A3 = chemprop 2.1.0 的官方 MPNN，超参取官方默认。**
`BondMessagePassing(d_v=72, d_e=14, d_h=300, depth=3, dropout=0)` + `NormAggregation(norm=100)` + `RegressionFFN(300×1)` + Noam 式学习率（`1e-4 → 1e-3 → 1e-4`，warmup 2 轮），这些全是 chemprop `train` 子命令的默认值（本机 2.1.0 实测读出，不是照记忆写）。分工书明写的 `batch 64 / max_lr 1e-3 / ≤100 epoch / patience 15` 是唯一的四处显式值。**红线 2 的意义**：A3 要是"我调到最好的一版"，H3 就从"信息 vs 架构"变成"信息 vs 我调的超参"。

**② 早停的验证集：PolyBench 官方没有，用训练集内部固定 10%。**
PolyBench 只发 70/30，而 `patience 15` 必须有东西可监控。做法：从**官方训练索引内部**切 10%（`val_split_seed=20261121`，**三个模型种子共用同一份**），测试集一次都不碰，也不进任何指标。PB26/OpenPoly 有官方验证集，直接用。记录里的 `val_source` 字段写清是哪种：`official` 还是 `inner_10%_of_train`。

**③ 标签标准化只用训练集统计量，而且喂给损失的标签必须也是标准化的。**
这条是本任务唯一踩到的真坑，且它**不报错**：

> `chemprop.nn.UnscaleTransform.forward` 在 `self.training` 为真时**原样返回输入**，只有 `model.eval()` 之后才做 `x * scale + mean`（源码如此）。所以训练/验证阶段网络输出活在**标准化空间**，喂给 criterion 的标签也必须是 `(y − mean) / scale`。喂原单位会让网络去追原单位的数值，而在预测时再乘一次 scale——
>
> 实测后果：真值 618 K 被预测成 **98,564 K**（约 180 倍），`pb_t1_tg` 的 R² 变成 **−189,524**。看起来像"模型完全不收敛"，其实是单位错了一层。
>
> 修正后同一份配置 20 轮就到 R² 0.848、RMSE 42.7 K。这也是 chemprop 官方流程在建 dataloader 前调 `normalize_targets()` 的原因。

代价写在记录里：`val_loss` 是标准化单位的 RMSE，`best_val_rmse` 已乘回 `scale` 与原单位同尺，`val_loss_normalized` 原样保留便于和 chemprop 日志对拍。

**④ `split_version` 记的是"这一折自己的文件"的哈希。**
PolyBench 一个任务一个 JSON（整份就是那一折）；PB26 的 `manifest.json` 只描述五折，真正定义折的是 `fold_XX.npz`；OpenPoly 是五个 JSON、`SplitSpec.sha256` 是五份拼接。所以 `fold_version()` 按基准取到**折文件**再算哈希，格式 `<12 位>@splits/...`，并另存 `split_fold_sha256`。只记 manifest 的哈希，换掉一折时记录不会有任何变化。

**⑤ 确定性要两条腿，而且 Lightning 会把你钉的那一条悄悄关掉。**
这条是本任务第二个真坑，且它**不报错、不警告**，只有把两次结果摆在一起才看得见。

> 第一版只钉了 `torch.backends.cudnn.deterministic = True`（分工书原文要求的那一项），同 seed 连跑两次，`pb_t1_tg` 的预测**最大差 65 K**——不是"大致一致"，是肉眼可见地不一样。
>
> 根因有两条，缺一不可：
>
> 1. **cudnn 那条管不到这里。** chemprop 的图级聚合 `SumAggregation` / `NormAggregation` 是 `torch.zeros(...).scatter_reduce_(reduce="sum")`（`chemprop/nn/agg.py` 源码），它在 CUDA 上默认走**原子加**，同一个数加进去的先后顺序每次不同，浮点加法又不可交换。cudnn 只管卷积那类算子，与它无关。第二条腿是 `torch.use_deterministic_algorithms(True)`。
> 2. **`pl.Trainer(deterministic=False)` 在构造时主动调用 `torch.use_deterministic_algorithms(False)`。** 也就是说：外面设了 strict、Trainer 传 False，进去就被抹掉——**开关写了等于没写**。本机实测这一行 `Trainer(deterministic=False)` 之后 `torch.are_deterministic_algorithms_enabled()` 从 `True` 变成 `False`；传 `True` 才是 `True`。
>
> 修法：用**同一个变量**喂两边（`torch.use_deterministic_algorithms(deterministic)` 与 `Trainer(deterministic=deterministic)`），并把 `CUBLAS_WORKSPACE_CONFIG=:4096:8` 放在模块层设置——它必须在进程第一次调 cuBLAS **之前**生效，放进 `train_one()` 就晚了。
>
> 修完的实测：同 seed 两次**逐位相同**（最大差 `0.0`，测试集 2,417 个点全等，两次 r2 到小数点后 16 位一致）。**代价约 1.6 倍墙钟**（单条 60 秒 → 98 秒），已计入 §5 的预算。

为了让"关掉确定性"不能悄悄发生，这条写成了**校验**而不是注释：每条 `device=cuda` 的记录 `gpu` 块里同时记 `cudnn_deterministic` 与 `deterministic_algorithms`（后者读的是**实际生效状态**，不是配置里的意图），`record_problems()` 见到任何一个是 `false` 就判这条记录不合格。B-5 复用训练器时也逃不掉这道闸。

**可复现性（验收④）**：`--repeat-check 2` 在 `pb_t1_tg`（5,074 张训练图，最大的一档）上把**同一份配置、同一折、同一种子**连跑两次，两次测试集预测的最大绝对差记在 `results/aggregate/a3_repeatability.json`。

**结果：最大绝对差 `0.0`，中位差 `0.0`，超过 1e-3 的点 `0 / 2,417`。** 两次的 r2 到小数点后 16 位完全相同（`0.8840909602834374`），轮数都是 78，单次 98 秒。也就是说这不是"小于阈值"，是**逐位相同**——把 P4 那一行验收标准里的"同 seed 两次结果逐位相同"真正兑现了。同一个检查在修之前（只钉 cudnn）给出的是 **65 K**。

> 这个数怎么来的、为什么不是"硬件做不到"，写在 §3 ⑤：`Trainer(deterministic=False)` 会主动关掉 `use_deterministic_algorithms`，而那正是唯一能管住 CUDA 上 `scatter_reduce` 原子加的开关。

## 6. 三个低分的任务，为什么不是坏消息

`pb_t3_iwlt`（R² ≈ 0.02）、`pb_t3_dielectric_loss`（R² ≈ −0.01）、`pb_t3_dmp_sm` 这一层在 proposal 里本来就是"重复单元解释不了"的候选：

- **`pb_t3_iwlt`（IwLT，228 行）**：构造上依赖**时间与温度**，重复单元是同一根链，IwLT 却随测试条件变——A3 拿不到温度，学不到是应当的；
- **`pb_t3_dielectric_loss`（279 行）**：介电损耗由**频率**决定，同一材料在不同频率下差几个数量级，而 A3 的输入里没有频率；
- 这两个任务的 R² 接近 0，正是 H2（"Λ 大"）**预期的形状**：如果它们也到 0.8，反而说明测试集泄漏了什么。

对照：`pb_t1_tg` ≈ 0.89、`pb26_polymetrix_tg` ≈ 0.89 —— 玻璃化温度由链的化学组成主导，重复单元能解释，这与文献一致。**A3 不是"跑不出数"，是"该高的高、该低的低"**，这条本身就是管线正常的旁证。

> **给 D 的提醒**：这三个任务的 R² 低会让 Λ 变大（Λ 是"最优可达 − 实际"的差），而 Λ 的**置信区间**会随样本量（69–84 个测试点）变得很宽。bootstrap 直接用 `predictions/*.parquet` 的 `row_id` 回表取标签，不要用记录里的 `n_test` 自己造索引。

## 8. 没做到的

1. **`pb26_arch_transfer_ea` / `pb26_scaling_cp` 没有 run**：它们是机制实验（C-4 / C-5），不是主表 8 任务；B-3 的 48 条按分工书只含主表任务。要跑得先由 C 定实验网格。
2. **B-5 的 225 条没有跑**：那是另一个任务项（`openpoly_scan.yaml` + 三个性质 × 5 档 × 5 折 × 3 种子），按分工书要和主扫**分两夜**，不许抢卡。训练器已经能跑 OpenPoly（`load_split` 认 `openpoly` 基准、`dedupe=False` 的行表照样喂），只差那份扫参配置。
3. **没有做超参搜索**：这是**故意的**（红线 2）。A3 是"官方标准配置"，调参会让 H3 失真。要调请在 C 的机制实验里另开一条臂，不要改这份 `a3_graph.yaml`。
4. **`num_workers=0`**：图已经在内存里，多进程只把 collate 变成 IPC；GPU 利用率约 30%，说明瓶颈在数据搬运而不是算力。若要提速，先改配置再全表重跑（`config_hash` 会变），不能"边跑边改"。
5. **权重没入库**：`.ckpt` 跑完即删。要复现某一条 run，用 `config_hash` + seed 重跑；两条确定性开关都钉着，结果是**逐位相同**而不是"大致一致"（§5 的实测）。
